# Managed language support: verified scope

Checked 2026-11-18 on macOS arm64. Catalog entries describe adapters and prerequisites, not a promise that every LSP method works. `capabilities_buffer` returns the negotiated capability object. Unsupported methods fail explicitly. Push diagnostics without a matching document version remain unavailable; synchronous pull diagnostics are bound to the current snapshot. Viewing and text search never require installation or analysis.

All rows below use authored temporary Git repositories. Runtime processes use absolute app-owned executables and a short PATH; no Homebrew, Python, npm, Go, Rust or Java executable from the developer's PATH is required. Installed runtime/tool artifact versions, URLs and digests are recorded in `managed-tools.json`. A successful install does not change project trust or launch analysis.

## Primary sources and licensing

Official repositories and root SPDX observations are recorded in [upstream-research.json](upstream-research.json). Those observations are **not** complete binary redistribution grants. Package archives retain their legal material. Source-built Go tools retain dependency legal files and exact compiled-module checksums; source/JAR Groovy pins are in [managed-pins.json](managed-pins.json). For artifacts without an official strong checksum, that file or recipe contains a reviewed app-catalog SHA256 pin, rather than calling a locally computed digest an upstream publication.

The [official Kotlin README](https://github.com/Kotlin/kotlin-lsp#project-status) explicitly states that the distribution includes proprietary parts. Root Apache SPDX does not grant rights to redistribute the complete distribution; the backend rejects a Kotlin package in the bundled manifest. Packaging performs complete Temurin/JDT notices and corresponding-source review separately. No paid IntelliJ unified server is installed.

The [Spring Boot README](https://github.com/spring-projects/spring-tools/blob/main/vscode-extensions/vscode-spring-boot/README.md) documents `application*.properties`, Java tooling requirements and project metadata. Actual bridge requests are in [classpath.ts](https://github.com/spring-projects/spring-tools/blob/main/vscode-extensions/commons-vscode/src/classpath.ts) and [java-data.ts](https://github.com/spring-projects/spring-tools/blob/main/vscode-extensions/commons-vscode/src/java-data.ts). The [launcher](https://github.com/spring-projects/spring-tools/blob/main/vscode-extensions/vscode-spring-boot/lib/Main.ts) requires Java 21+, defers classpath listeners until client callbacks are registered, and registers both services. Forkarak currently refuses arbitrary execute-command requests, has none of these STS bundles or bridges, and therefore honestly does not route Spring Properties to bare JDT.

## Reproducing validation

`tests/managed_real.rs` installs nothing. Set `FORKARAK_MANAGED_TOOLS_DIR` to an explicitly prepared app-owned directory and run ignored tests on a background terminal. Set `FORKARAK_BUNDLED_RESOURCES` to an actual packaging output to exercise `real_bundled_java_resource_manifest`. Each test creates its own temporary repository. The live `InstallControl` drives the developer-only `managed-tools` example; production native UI uses the same API and requires no terminal interaction from the user.
